# Repair Policy

The incremental JSON parser is designed to handle malformed input gracefully, particularly common anomalies generated by Large Language Models (LLMs). This document outlines the repair policy.

## What Repair Means
A "repair" is an action taken by the parser to coerce invalid or incomplete syntax into a valid JSON structure in the `stableValue`, allowing partial data extraction.

## Impact Levels
Every repair action is classified by its impact:
- **`representation_preserving`**: Semantics are untouched.
- **`root_preserving`**: The core document structure is maintained.
- **`structural`**: Missing brackets/braces were inserted to close containers.
- **`lossy`**: Data was discarded or altered to maintain validity.

## This Milestone
In the current milestone, **no advanced repair is implemented**. The parser focuses on strict structural adherence and precise diagnostic emission. 

## Future Milestones
Future milestones may implement targeted repairs for common LLM errors, such as:
- Auto-closing open containers at stream termination.
- Handling missing commas.
- Stripping isolated trailing text.

## Explicit "Never Repair" List
The parser is a data extractor, not a data synthesizer. It will **NEVER**:
- Guess partial string contents.
- Fabricate incomplete Unicode escapes.
- Add missing digits to incomplete numbers.
- Predict commas or colons arbitrarily without clear context.
- Generate artificial field values for missing keys.
- Call out to an LLM for context resolution.
- Invent, hallucinate, or insert user data under any circumstances.
